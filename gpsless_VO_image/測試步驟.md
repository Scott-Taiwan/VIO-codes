# 手持測試步驟（不用飛行）

用 `live_vo_gps.py --handheld` 在地面手持 F450 走動，測試「連續拍照 → VO → dead-reckoning」這條流程，不用真的起飛。

## 0. 測試前準備

1. **拆掉螺旋槳**（不管待會要不要接飛控通電，這是強制的安全措施）。連線、讀遙測、送 `GPS_INPUT` 都不會讓飛機解鎖(arm)或動馬達（解鎖需要遙控器/地面站明確下指令，這支程式從頭到尾不會送這種指令），但拆槳仍是保險，跟有沒有用 `--dry-run` 無關。
2. 選一個地面有紋理的地方（磁磚接縫、草地、柏油、地毯花紋都可以），避免單色地板/桌面——SIFT/ORB 才找得到足夠特徵點。
3. 決定要用哪種供電方式（見下方兩種指令擇一）。
4. 鏡頭離地建議至少 1m 以上（例如像端托盤一樣舉在胸前往下拍）——IMX219 是定焦鏡頭，太近可能會失焦模糊。

## 1. 執行指令

**情境一：只有 Jetson + 相機供電，完全不碰飛控**
```bash
python3 live_vo_gps.py --handheld --dry-run --interval 1 --save-dir ./handheld_test
```

**情境二：F450 整台通電、飛控跟 Jetson 序列埠有接好**（拿真實羅盤航向/GPS 當錨點，軌跡方向會更準）
```bash
python3 live_vo_gps.py --handheld --port /dev/ttyTHS1 --interval 1 --save-dir ./handheld_test
```

## 2. 啟動當下會看到什麼

先是安全提醒橫幅（`--handheld` 觸發的）：
```
======================================================================
HANDHELD TEST MODE -- ground test, not a real flight.
SAFETY: propellers must be removed before handling the frame,
whether or not the flight controller is powered on.
No Pixhawk connection (--dry-run) -- using a dummy anchor.
======================================================================
```
情境二的話最後一行會換成 `Connecting to Pixhawk for a real compass heading/GPS fix...`，並在這之前多印一行：
```
Connecting to /dev/ttyTHS1 @ 57600 baud ... OK sys=1 comp=1
```
（如果 10 秒內收不到飛控的 heartbeat，程式會直接報錯退出）

接著印出錨點與參數：
```
Anchor: 0.0000000, 0.0000000  alt_msl=0.0m  agl=1.5m  heading=0deg
Capture interval: 1.0s   GPS_INPUT resend rate: 5.0 Hz

Camera open. Ctrl+C to stop.
```
- 情境二如果飛控有給到真實羅盤航向，`heading=` 這裡會是實際角度，不是 0
- 如果室內沒有 GPS 定位，`lat/lon` 還是會補 0，這是正常的，不用理會那組座標

## 3. 測試進行中（邊走邊看）

**第一張照片不會印出任何東西**（因為還沒有「前一張」可以比對）。從第二張開始，每隔 `--interval` 秒印一行，長這樣（示意，實際數字依現場拍攝內容而定）：

```
[frame 2] [OK  ] dt=1.02s detect=180ms match=45ms  disp=0.34m yaw=+2.10deg  -> 0.0000031,0.0000000 alt=1.5m hacc=0.68m
          https://www.google.com/maps?q=0.0000031,0.0000000
```

逐欄位意思：

| 欄位 | 意思 |
|---|---|
| `[frame N]` | 第幾張照片 |
| `[OK / LOW-CONF / FAIL]` | 這一段的信心標記。`OK`＝inlier 比例夠高、位移可信；`LOW-CONF`＝匹配到了但比例不夠（可能地面重複紋理或位移太大導致重疊不足）；`FAIL`＝連 inlier 數量門檻都沒過，這一段完全沒有可用的位移資訊 |
| `dt=` | 跟上一張間隔幾秒 |
| `detect=` / `match=` | 這一輪迴圈中「算力」部分各花多少毫秒（特徵偵測／比對+RANSAC）。兩者加起來如果超過 `--interval` 設的毫秒數，代表 `--interval` 設太短、CPU 追不上，會看到整體變慢——這就是回答「一秒能處理幾張」的實測依據 |
| `disp=` / `yaw=` | 這一段估算出的位移量（公尺）跟旋轉角度。只有 `OK`/`LOW-CONF` 才會印；`FAIL` 時這裡會換成原因說明，例如 `(too few inliers)` |
| `-> lat,lon alt=... hacc=...` | 套用這段位移後，`PositionTracker` 目前算出的座標／高度／水平精度估計。`hacc` 會隨著累積的 `LOW-CONF`／`FAIL` 段數越來越大，持續往上爬就代表軌跡已經不可信了 |
| `maps_url` | 可複製貼到瀏覽器看座標畫在地圖上哪。情境一因為錨點是假的 `(0,0)`，這條連結沒意義可忽略；情境二如果飛控真的有 GPS 定位，才有參考價值 |

如果某一輪抓幀失敗，會單獨印一行 `WARNING: frame grab failed, skipping`，不影響後續繼續跑。

## 4. 停止測試

按 `Ctrl+C`，會印出總結，然後相機釋放、程式結束：
```
Stopped after 23 frames, 22 leg(s). Final: 0.0000031,0.0000000 hacc=3.42m
```

## 5. 測試後：照片存在哪、怎麼分析

因為有加 `--save-dir ./handheld_test`，這個資料夾裡會有每一張擷取到的照片，檔名格式是 `YYYYMMDD_HHMMSS__live__<高度>m.jpg`（例如 `20260716_143022__live__1.5m.jpg`）。這個雙底線格式跟 `visual_odometry.py` 內建的高度解析規則對得上，所以之後直接重跑：
```bash
python3 visual_odometry.py ./handheld_test/
```
就會自動從檔名讀到正確的高度（例如 1.5m），不用再手動加 `--altitude` 覆蓋——不會像早期版本那樣悄悄退回 `config.py` 裡飛行用的 `REFERENCE_ALTITUDE_M = 60.0`。

這個離線重跑的版本畫面會比即時 log 更完整（含每段跟檔名 GPS ground truth 的比對——這邊沒有意義因為沒有真 GPS——以及最後印出的完整軌跡表）。

## 6. 想驗證準確度的話

可以事先用皮尺量好一段已知直線距離（例如手持沿地板走 5 公尺），事後跟程式估算的軌跡比對誤差。人走路速度比飛行慢很多，同樣 `--interval` 秒數下連續照片的重疊度會高很多——這正好可以驗證 `summary.md` 提到的「拍照間隔要夠密才準」這個結論。
